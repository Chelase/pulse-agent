# 共享数据模型

本目录存放手表 Agent 与外部生态其他设备之间共享的数据形状定义。

**判据：别的设备需要知道这件事吗？** 需要就放这里，不需要就留在 `blueos/`。

| 文件 | 作用 |
|------|------|
| `gate-conditions.schema.json` | 闸门条件的格式定义（JSON Schema） |
| `gate-conditions.json` | 默认闸门条件集 |
| `api-modes.json` | LLM 请求协议模式清单（id / 显示名 / 端点末尾路径 / 鉴权头）；控制面下拉与表上适配器共用，Bedrock Converse 因需 SigV4 签名列为不支持 |

## 闸门是什么

Agent 的四步闭环是「感知 → 闸门 → 思考 → 输出」。闸门是感知和 LLM 之间的廉价前置过滤器。

心率传感器可能每秒一个读数，一天 86400 个。每个都问一次 LLM 会同时炸掉三样东西：**钱**（每次 API 调用计费）、**电**（手表电池撑不住）、**响应速度**（每次要等网络往返）。

所以先用便宜的规则筛一遍，只有可疑的才交给 LLM。

## 为什么必须是声明式数据

同一条规则有两种写法：

```js
// 命令式 — 写在代码里
if (hr > 100 && duration > 600) { askLLM() }
```

```json
// 声明式 — 写成数据
{ "dataType": "heart_rate", "operator": "gt", "threshold": 100, "sustainedSeconds": 600 }
```

本项目选后者，三个理由：

1. **外部系统能读懂。** 外部系统想知道「手表在什么情况下会上报异常」，它能读 JSON，读不懂你的 `if` 语句。
2. **改配置不用改代码。** 阈值从 100 调到 110，改一个数字，不用重新打包 `app.rpk`。
3. **能翻译成硬件能力。** 部分平台的传感器芯片可以自己判阈值、不唤醒 CPU。声明式条件能直接翻译过去，`if` 语句翻译不了。

## 闸门与 LLM 的职责边界

**闸门只做单信号的廉价比较，不做上下文融合。**

「心率 130 + 步频为零 + 不在运动模式 + 日历上写着绩效评审 → 这是压力不是运动」——这种融合是 LLM 的活，不要试图用闸门条件表达。闸门只负责把「心率 130 且持续了 10 分钟」这件事捞出来，剩下的判断交给 LLM。

这条边界也是为什么 schema 里没有组合条件（AND / OR）：一旦开始组合，就是在用错误的层做 LLM 的工作。

## 关键字段说明

- **`sustainedSeconds`** — 条件要连续满足多久。滤掉瞬时抖动（比如手腕一动导致的单次心率跳变）。
- **`cooldownSeconds`** — 触发后的静默期。**这个字段是必填的**：缺了它，一个持续偏高的心率会在每个采样点都触发一次，把 LLM 调用打爆。

## 实现侧约定

BlueOS 侧读取 `gate-conditions.json` 并在本地求值，不把原始采样流送进 `agent-loop`。跨过闸门的事件才调用 Agent。

默认条件集只包含**已有采样来源**的条件：心率偏高、心率偏低、手表被取下。`blood_oxygen` 与 `battery_level` 虽在 schema 的枚举里，但当前没有对应的桥接实现，不写进默认条件集——没有采样来源的条件留在集里只会让接入方误以为该能力可用。
